# ADR-003 后端形态架构决策（模块化单体 vs 微服务）

- **status**: Proposed
- **date**: 2026-10-08
- **背景与约束**：
  TripCraft 后端包含 10 个逻辑功能模块（S-IDENTITY 至 S-OPS）。当前团队规模小，初期重在快速验证 B2B2C 商业模式与首批 3–5 家地接社试点。需避免过早引入分布式服务带来的网络运维负担与部署成本。

- **选项对比**：
  - **选项 A：模块化单体架构 (Modular Monolith)**
    - *优点*：代码全量位于单一代码库或 Monorepo，模块间通过强类型进程内调用解耦；本地极易一键运行调试；数据库事务完整可靠；运维容器极简。
    - *代价*：单一组件崩溃可能影响全进程（可通过进程看门狗缓解）；技术栈受限为同一种主流后端语言。
    - *风险*：若团队自律性不足，可能导致模块间代码边界逐渐腐化穿透。
  - **选项 B：微服务架构 (Microservices Architecture)**
    - *优点*：各服务可独立伸缩、独立部署，技术栈自由。
    - *代价*：需要全套 API 网关、服务注册发现、分布式链路追踪与分布式事务；机器资源与云厂商开销显著增加。
    - *风险*：对小团队研发人效造成毁灭性消耗，过早优化导致项目进度停滞。

- **评估标准**：团队交付人效、初期云资源成本、系统运维复杂度、未来可拆分演进性。

- **建议决策 (Proposed)**：
  **采纳选项 A**。初期坚决采用 **模块化单体架构 (Modular Monolith)**。
  以严格的包目录规范界定 S-IDENTITY、S-WORKSPACE 等模块边界；模块间只通过显式接口调用与内部事件通信；未来若某个模块（如 AI 生成计算）出现算力瓶颈，可物理剥离为独立微服务。

- **影响**：
  团队可基于单一容器快速完成本地与生产部署；CI/CD 流水线极大简化。

- **重新评估的触发条件**：
  后端研发团队规模扩展至 10 人以上，或单个模块算力/网络吞吐出现严重物理瓶颈时重新评估。
