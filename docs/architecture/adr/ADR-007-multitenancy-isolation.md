# ADR-007 多租户隔离方式架构决策

- **status**: Proposed
- **date**: 2026-10-08
- **背景与约束**：
  B 端机构（地接社、车队）对私有客户名单、内部特许资源（特窟配额）以及商业报价敏感度极高（关联 [ARC-06 多租户架构](../ARC-06-multitenancy-whitelabel.md)、[docs/03 §3.2](../../03-b2b-agency-operations.md#32-角色模型与权限矩阵)）。系统必须保证租户间数据绝不穿透，同时兼顾运维低成本。

- **选项对比**：
  - **选项 A：共享数据库 + 行级安全策略 (Shared Database with Row-Level Security, RLS)**
    - *优点*：基础设施成本最低，单实例 PostgreSQL 即可承载数百家中小机构；数据库原生 RLS 策略在引擎层强制校验 `tenant_id`，防止应用层代码疏漏导致越权；架构极其平滑。
    - *代价*：共享数据库计算与连接池，需要防范个别大租户流量尖峰影响相邻租户。
    - *风险*：若数据库连接池未正确清理上下文 Session 变量，可能存在上下文污染。
  - **选项 B：独立 Schema 隔离 (Schema-per-Tenant)**
    - *优点*：数据表物理隔离在不同 Schema，逻辑边界更清晰。
    - *代价*：每次系统迭代 DDL 迁移需要遍历成百上千个 Schema，数据库连接池管理复杂；元数据膨胀明显。
    - *风险*：数据库迁移脚本极易发生部分失败导致状态不一致。
  - **选项 C：独立数据库隔离 (Database-per-Tenant)**
    - *优点*：隔离级别最高，彻底消除串门与邻居干扰风险。
    - *代价*：初期基础设施成本极其高昂，运维极度繁重，严重超出小团队支撑能力。
    - *风险*：在商业模式未规模化前造成巨大的资金与运维浪费。

- **评估标准**：安全性与合规性、初期运维复杂度、数据库扩展与备份便利度、基础设施成本。

- **建议决策 (Proposed)**：
  **采纳选项 A**。采用 **共享数据库 + PostgreSQL 原生行级安全策略 (RLS)**。
  所有租户业务表强制绑定 `tenant_id`；ORM/查询中间件统一注入 `SET LOCAL app.current_tenant_id`；对机构最高机密的特许资源表与客户身份证进行列级应用层二次加密存储。

- **影响**：
  保持极高的运维敏捷度；兼顾了对小 B 客户隐私资产的物理/逻辑隔离承诺。

- **重新评估的触发条件**：
  当签约大型品牌文旅集团，客户明确提出合规审计要求必须做物理独占数据库时，为该顶级客户提供单独的独立私有化部署。
