# ADR-002 同步与冲突模型选择

- **status**: Proposed
- **date**: 2026-10-08
- **背景与约束**：
  自驾行程存在严重的弱网、断网及长周期离线编辑场景（关联 [S-C04](../../product/PRD-03-scenarios.md#s-c04-断网--无人区离线使用)、[S-C05](../../product/PRD-03-scenarios.md#s-c05-行中突发变更与全员同步-plan-b-熔断)、[A-08](../../ASSUMPTIONS.md)）。系统需要支持团队成员离线记录变更，联网后平滑合并，并在无人区通过二维码点对点派发增量补丁（`TripPatch`）。

- **选项对比**：
  - **选项 A：服务端权威版本号 + 增量操作日志 (Server-Authoritative Operational Log + 3-Way Merge)**
    - *优点*：模型直观，天然对应 [`spec/patch.schema.json`](../../../spec/patch.schema.json) 的语义化原子操作（`shift`, `replace`, `skip` 等）；冲突仲裁规则易于人眼核验与领队拍板；无冗余元数据开销。
    - *代价*：当离线并发分叉严重时，需要启发式三方合并逻辑或人工介入确认。
    - *风险*：在超大规模多人同时实时打字编辑时存在锁冲突（但在自驾行程低频编辑场景下极罕见）。
  - **选项 B：无中心纯 CRDT 算法库（如 Yjs / Automerge）**
    - *优点*：数学上保证强最终一致性，完全不依赖中心化服务器即可自动收敛任意并发合并。
    - *代价*：CRDT 内部包含庞大的 Lamport 时间戳与 Tombstone 删除标记，增量数据体积膨胀数倍，**无法装入二维码容量限制（QR Code ≤ 2KB）**；且自动合并往往产生违反业务逻辑的怪异行程（如同一时段安排两个景点）。
    - *风险*：调试与排查极困难，引入黑盒第三方库与单文件交付零依赖铁律冲突。

- **评估标准**：补丁体积（必须能打入单张二维码）、业务语义理解度（开闭馆与时间冲突合规性）、实现与调试复杂度。

- **建议决策 (Proposed)**：
  **采纳选项 A**。采用 **服务端权威版本号 + 领域语义化增量操作日志**。
  在线状态以递增 `revision` 服务端日志为准；离线状态以 `patch.schema.json` 结构打包操作序列；冲突时坚持“领队拍板优先 + 人工显式二选一”，不采用无监督的纯数学 CRDT。

- **影响**：
  增量补丁可以直接被二维码承载；前后端需统一实现基于 `baseRevision` 的三方合并器（Three-Way Merger）。

- **重新评估的触发条件**：
  若未来业务场景演进为类似多人实时在线协作白板的高频并发打字共创，导致锁竞争过高时重新评估。
